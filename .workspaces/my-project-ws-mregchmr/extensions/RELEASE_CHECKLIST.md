| Cursor `extension.ts` | `/api/mcp-config` | GET | — | — | same as above | ✅ |

**Audit findings (filed under "Known Issues" below):**
- ✅ Chrome ↔ `/api/github/scan-real` and `/api/vault` — shape match, no fix needed.
- ❌ VS Code `scanWorkspace` previously POSTed `{ repoUrl: "vscode-workspace" }` to `/api/scan`. In V20 `/api/scan` delegates to `scanGitHubRepo` (`src/lib/github-scanner.ts:76`) which calls `https://api.github.com/repos/${repo}` — `"vscode-workspace"` is not a valid `owner/name`, so the scan would always fail with `GitHub API 404`. **FIXED** in `extensions/vscode/src/extension.ts`: scanWorkspace now scans open documents **locally** with the byte-identical detector port (`src/detector.ts` ≡ `src/lib/security/detector.ts`) and applies the SAME `computeTrustScore` + `scoreToGrade` formula from `src/lib/scanner.ts`. No `/api/scan` round-trip; the `/api/vault` POST path is unchanged.
- ❌ Cursor `package.json` declared `"main": "./out/extension.js"` but `tsc -p .` (with `rootDir: ..`) emits `./out/cursor/src/extension.js`. The extension would fail to activate. **FIXED** in `extensions/cursor/package.json`.
- ⚠️ `/api/vault` and `/api/github/scan-real` both fall back to `anonymousContext()` when no `Authorization` header is present (`getContext(req) || anonymousContext()`), so the extensions work without an API key against a local dev backend. Production should require an API key (see V20 reality report item #10 — auth gap).

### Response-shape verification

- `/api/github/scan-real` returns `{ ok: true, ...RealScanResult }` where `RealScanResult`
  (`src/lib/github-scanner.ts:21`) has `repo`, `filesScanned`, `files`, `findings`,
  `secretsCount`, `configsCount`, `vaultedCount`, `score`, `grade`. Chrome's
  `background.js` reads `score`, `grade`, `filesScanned`, `secretsCount`, `vaultedCount`,
  `findings.length` — all present. ✅
- `/api/vault` GET returns `{ secrets, count }`. Chrome popup reads
  `data.count ?? data.secrets.length` — both branches satisfied. ✅
- `/api/vault` POST returns `{ ok: true, secret: { id, name, provider, scope, masked } }`.
  VS Code `protectSecrets` reads `res.data.secret?.id` — present. ✅
- `/api/mcp-config` returns `{ server: { name, protocolVersion }, configs, instructions }`.
  Both VS Code `connectMcp` and Cursor `cursorMcp` read these — present. ✅

### 1.3 Known limitations

- **No MCP connect command.** The Chrome extension does not surface MCP config;
  use the dashboard (`/api/mcp-config`) or the VS Code / Cursor extension instead.
- **No restore flow in the popup.** Vault entries are listed as a count only;
  there is no UI to retrieve/restore a masked secret. Use the web dashboard.
- **API key is stored in `chrome.storage.local`** (unencrypted). Sufficient for
  a developer tool, but not for shared machines. **UNVERIFIED** whether Chrome's
  storage is encrypted at rest on every platform.
- **Scan results are limited to 30 files** by the backend
  (`src/lib/github-scanner.ts:94` slices `files.slice(0, 30)`). Large repos are
  under-scanned.
- **Rate limits.** GitHub's unauthenticated REST limit (60 req/h per IP) will
  throttle rapid scans. The extension does not pass a GitHub token today — only
  the ShadowPaste API key is sent. To scan private repos or lift the rate limit,
  the user must wait for a future extension update that adds a `token` field
  (the route already accepts `token` in the body, per `/api/github/scan-real`).
- **`host_permissions` includes `localhost:3000` only** by default. Production
  deployments on HTTPS hosts require editing `manifest.json` `host_permissions`
  before publishing to the Chrome Web Store.

### 2.3 Known limitations

- **`scanWorkspace` runs locally; it does NOT persist a project/scan row in the
  backend.** The backend's `/api/scan` route persists a `Project` + `Scan` row
  in Prisma and writes an `auditLog` entry. The local scan in the extension
  does not — the findings are shown in the Webview only. If persistence is
  required, run the scan from the web dashboard instead.
- **`scanWorkspace` scans only currently-open text documents**, not the entire
  workspace folder. Files not opened in an editor are skipped. (Mitigation: open
  all files first, or use the dashboard's GitHub scan for full-repo coverage.)
- **Local detector is a byte-identical port.** `src/detector.ts` must be kept
  in sync with `src/lib/security/detector.ts` manually — there is no build-time
  guard. If the backend patterns change, update both files together.
- **Local score formula mirrors `src/lib/scanner.ts`.** Same manual-sync risk
  applies to `computeTrustScore` (deductions `{critical:25, high:12, medium:5, low:2}`)
  and `scoreToGrade` thresholds.
- **No restore command.** Once a secret is virtualized in the document and
  stored in the vault, the extension does not provide a "de-virtualize" command
  to swap the reference back for the raw secret. Use the web dashboard.
- **No config scan.** The backend's `scanGitHubRepo` also scans for risky
  configs (`*:*` IAM, `privileged: true`, TLS-disabled, etc.) via
  `CONFIG_PATTERNS`. The extension's local scan does NOT — it only finds
  secrets. (The `detector.ts` port has no `CONFIG_PATTERNS` block.)
- **Workspace scan score is informational.** Because the extension does not
  persist a scan, the score shown in the Webview is the only place it lives —
  it will not appear in the dashboard's project list or the trust leaderboard.
- **`engine.vscode: ^1.80.0`** — older VS Code versions are not supported.

### 3.3 Known limitations

- **Inherits all VS Code extension limitations** (§2.3) because it re-exports
  `activate` / `deactivate` from `../../vscode/src/extension`.
- **The `cursorMcp` command writes a file the user must manually save** to
  `~/.cursor/mcp.json`. There is no auto-write — by design, to avoid touching
  the user's home directory without consent.
- **`<your-agent-api-key>` placeholder in the config** must be manually replaced
  with a real ShadowPaste agent API key. The extension does not have access to
  the user's agent keys (they live in the backend's `Agent` table).
- **Cross-extension import.** `src/extension.ts` imports from
  `../../vscode/src/extension`. This means the VS Code extension's source must
  be present at build time. If `extensions/vscode/src/extension.ts` is moved or
  renamed, the Cursor extension breaks.
- **Build output layout.** Because `tsconfig.json` uses `rootDir: ".."`, the
  compiled JS is emitted at `out/cursor/src/extension.js` and
  `out/vscode/src/extension.js` (not `out/extension.js`). The `package.json`
  `main` field has been updated to match — do not revert it.
- **No separate Cursor permission UI.** The zero-trust permission prompt is
  served by the backend's web dashboard, not by the editor. Cursor's agent
  will be blocked silently until the user approves in the dashboard.

### 4.3 Auth flow

1. User obtains a ShadowPaste API key from the web dashboard (TBD — there is
   no `/api/agents/api-key` route today; keys are seeded via `/api/seed` for
   dev). **UNVERIFIED** that a user-facing key-issuing flow exists.
2. User pastes the key into the extension's settings (Chrome popup / VS Code
   settings / Cursor settings).
3. Every extension `fetch` attaches `Authorization: Bearer <apiKey>` IF a key
   is set; otherwise the request goes anonymous.
4. Backend `getContext(req)` resolves the key to a `User` + `Org`; if missing,
   `anonymousContext()` is used (orgId: `"default"`). **UNVERIFIED** that the
   backend actually enforces auth on these routes in production — the V20
   reality report flags 23/31 routes with no auth check (item #10).
5. The Cursor MCP config returned by `/api/mcp-config` embeds a
   `<your-agent-api-key>` placeholder in `headers.Authorization` — the user
   must replace it manually before saving `~/.cursor/mcp.json`.

### 4.4 Phase-1 invariant ("the same secret behaves the same everywhere")

- The VS Code extension's `src/detector.ts` is a **byte-identical** port of
  `src/lib/security/detector.ts`'s `SELF_CONTAINED` + `ASSIGNMENT` patterns.
- The local `computeTrustScore` + `scoreToGrade` formula in
  `extensions/vscode/src/extension.ts` mirrors `src/lib/scanner.ts:108-124`
  exactly (deductions `{critical:25, high:12, medium:5, low:2}`, grade
  thresholds `A+ ≥95, A ≥90, B ≥80, C ≥70, D ≥60, F <60`).
- **Maintenance contract:** when either backend file changes, update the
  extension copies in the same PR. There is no build-time guard today — add a
  diff test (`tests/extensions/detector-parity.test.ts`) as a follow-up.

## 6. Known Issues (carried forward)

1. **VS Code `scanWorkspace` does not persist a Project/Scan row in the backend.**
   Mitigation: run a GitHub scan from the web dashboard for persistence. Fix
   path: add a new command `shadowpaste.scanGitHubRepo` that prompts for
   `owner/name` and POSTs to `/api/scan` correctly (route is already
   shape-compatible — accepts `{ repo: "owner/name" }`).
2. **VS Code `scanWorkspace` skips config-pattern findings** (no
   `CONFIG_PATTERNS` port). Mitigation: rely on the backend's GitHub scan for
   full coverage. Fix path: port `CONFIG_PATTERNS` from
   `src/lib/github-scanner.ts:35` into `extensions/vscode/src/detector.ts`.
3. **No restore/de-virtualize command in any extension.** Vault entries can be
   read in the dashboard but not inlined back into a document. Fix path: add
   `shadowpaste.restoreSecret` command that calls `GET /api/vault/{id}` and
   replaces `{{SHADOW_SECRET_*}}` references with the decrypted raw value
   (requires a new `/api/vault/[id]/reveal` route — currently no such route).
4. **API key storage is plaintext** in `chrome.storage.local` and VS Code
   settings. Acceptable for dev; for production, use Chrome's
